# 연결된 탑승자에게 초대하기

차량에 운전자 계정을 연결하고, 휴대전화의 ‘내 연결’에서 상대와 연결을 수락해 둔다.
그다음 차량에서 내비 장소를 확인하고 ‘연결된 탑승자에게 초대 보내기’를 누른다.
탑승자는 마중 웹의 `/account`에서 받은 초대를 수락하거나 거절한다. QR을 다시 찍을 필요는 없다.

## 처리 순서

1. 차량이 `GET /api/v1/vehicles/connections?page=0`으로 연결된 사람을 조회한다. 응답은 `items`, 한 페이지 20명이다.
2. `POST /api/v1/vehicles/invitations`에 `connectionId`, `requestId`, `place`를 보낸다. 응답이 불분명하면 같은 초대 번호로만 명시적으로 다시 보낸다.
3. `INVITED` 상태로 30분 동안 기다린다. 운전자는 `cancel-invitation`, 탑승자는 `accept-invitation` 또는 `reject-invitation`으로 응답한다.
4. 탑승자가 수락하면 `QUEUED` 상태가 된다. 수락 순서대로 기존 대기열에 들어가고, 현재 픽업이 끝나야 다음 건을 시작할 수 있다.
5. 차량이 기존 `start` API로 픽업을 시작하고 공유를 확인하면 기존 위치·준비 상태·도착·탑승 완료 흐름을 사용한다.

차량 API는 등록 차량의 Bearer 권한, 탑승자 API는 로그인 세션과 CSRF가 필요하다.
`ride-requests` 목록의 `driverInvitation`으로 운전자가 보낸 초대와 탑승자가 보낸 요청을 구분한다.

수락 전 위치 조회는 403이다. 수락 대기·픽업 대기 중 사람 연결이나 해당 차량의 운전자 계정 연결이 해제되면 초대를 사용할 수 없다.
초대를 보낸 차량에서만 그 픽업을 시작한다. 만료·거절·취소된 초대를 다시 수락할 수 없다.
이미 수락해서 진행 중인 픽업은 기존 종료 절차를 따른다.

## 기존 PostgreSQL 적용

서버 배포 전에 `src/main/resources/db/add-driver-invitation.sql`을 마중 DB에 한 번 적용한다.
새 DB는 `initial-schema.sql`에 포함돼 있다. 추가 컬럼은 `driver_invitation BOOLEAN NOT NULL DEFAULT FALSE`이며 기존 요청은 유지한다.
기존 서버도 추가 컬럼과 함께 실행할 수 있다. 새 서버는 컬럼이 없으면 배포 프로필의 스키마 검사에서 시작하지 않는다.

## 확인 범위

서버 통합 테스트에서 초대 중복, 수락 전 조회 차단, 다른 회원·차량 접근, 30분 만료,
거절·취소·연결 해제 및 기존 픽업 뒤 순차 시작을 확인한다.
웹을 닫은 동안의 푸시 알림은 아직 지원하지 않는다. 실제 휴대전화·실차 시험은 별도다.
