
# 픽업 자동 종료 및 데이터 보관 정책

마중 백엔드는 진행 중인 픽업이 방치되거나 차량 앱의 연결이 끊긴 상태로 복구되지 않는 경우를 처리하기 위해 자동 만료 정책을 적용한다.

픽업 상태와 마지막 정상 차량 활동 시각을 기준으로 만료 여부를 판단하며, 종료된 픽업과 연결된 요청 기록은 별도의 보관 기간에 따라 정리한다.

**탑승자 웹의 ETA 카운트다운이 0이 됐다는 이유만으로 픽업을 종료하지 않는다.**

---

## 1. 픽업 자동 만료 기준

픽업 상태에 따라 서로 다른 만료 기준을 적용한다.

| 상태 | 자동 만료 기준 | 시간 기준 |
| --- | --- | --- |
| `ACTIVE` | 정상 차량 활동 이후 30분 | 마지막 정상 차량 정보 수신 |
| `ARRIVED` | 도착 처리 이후 30분 | 최초 도착 처리 시각 |
| 공통 | 픽업 생성 후 최대 12시간 | 최초 생성 시각 |

### ACTIVE — 차량 활동 중단

`ACTIVE` 상태에서는 마지막 정상 차량 정보가 수신된 시점을 기준으로 30분의 유예 시간을 부여한다.

자동 연결 직후에는 처음 30분의 유예 시간이 적용된다.

새로운 정상 차량 정보가 들어오면 마지막 활동 시각을 갱신한다.

반면 오래된 SDK 정보를 재전송하거나 명시적으로 위치를 숨기는 요청은 정상 활동으로 계산하지 않는다.

### ARRIVED — 도착 후 미완료

`ARRIVED` 상태에서는 최초 도착 처리 시각부터 30분이 지나면 자동 만료한다.

다음 동작으로 도착 유예 시간을 연장하지 않는다.

- 동일한 도착 요청 반복
- 새로운 차량 위치·ETA 수신
- 탑승자의 준비 상태 변경
- 웹의 주기적 상태 조회

도착 상태와 실제 탑승 완료는 별개다.

운전자가 탑승 완료를 처리하지 않은 상태가 계속되면 만료 정책이 적용된다.

### 전체 12시간 상한

차량 정보가 계속 들어오더라도 픽업 생성 후 최대 12시간을 넘겨 유지하지 않는다.

이 상한은 `ACTIVE`, `ARRIVED` 상태의 개별 30분 기준과 별도로 적용된다.

**자동 만료 시점은 각 조건 중 먼저 도달하는 시점**이다.

---

## 2. 정상 차량 활동 판단

`ACTIVE` 상태의 활동 시각은 모든 API 요청으로 갱신하지 않는다.

| 동작 | 활동 시각 갱신 |
| --- | --- |
| 유효한 새 차량 위치·ETA 수신 | 갱신 |
| 탑승자의 준비 상태 변경 | 갱신하지 않음 |
| 웹의 픽업 상태 조회 | 갱신하지 않음 |
| 오래된 SDK 정보 재전송 | 갱신하지 않음 |
| 위치·ETA 명시적 숨김 요청 | 갱신하지 않음 |
| 중복 도착 처리 | 도착 유예 시간 연장하지 않음 |

서버는 차량 정보의 유효성 및 픽업 상태를 확인한 뒤 정상 활동 여부를 판단한다.

화면이 계속 열려 있거나 탑승자가 준비 상태를 반복 변경하더라도 픽업이 무기한 유지되지 않도록 한다.

---

## 3. 만료 처리

만료 조건에 도달한 픽업은 `EXPIRED` 상태로 전환한다.

### 만료 시 처리

- 픽업 상태를 `EXPIRED`로 변경
- 차량 위치 및 ETA 제거
- 초대 접근 권한 정리
- 연결된 도착 알림 구독 정리
- 이후 픽업 접근 및 상태 변경 제한

`EXPIRED`는 차량 앱과 모바일 웹이 기존에 처리하는 종료 상태다.

따라서 별도의 신규 종료 상태를 추가하지 않고 기존 종료 흐름과 연결한다.

### 만료를 확인하는 방법

마중은 두 경로에서 만료 여부를 확인한다.

**API 조회 시**

픽업을 조회할 때 현재 시각과 만료 조건을 비교한다.

**주기적 정리 작업**

별도 작업이 약 1분 간격으로 열린 픽업을 확인한다.

주기 작업은 한 번에 픽업 ID를 최대 100개씩 조회하고, 각 픽업을 개별적으로 잠가 처리한다.

100개를 초과하는 열린 픽업도 검사할 수 있도록 구성했다.

### 만료 시점과 작업 실행 시점

만료 조건의 기준 시각과 실제 정리 작업이 실행되는 시각은 구분한다.

예를 들어 마지막 정상 활동 이후 30분이 지나면 만료 대상이 되지만, 백그라운드 정리 작업은 다음 실행 시점에 이를 처리할 수 있다.

따라서 모든 픽업이 정확히 30분이 되는 순간 별도 작업에 의해 종료된다고 보장하지 않는다.

조회 시에도 만료를 확인하여 주기 작업 실행 전의 오래된 상태가 계속 사용되지 않도록 한다.

## 4. 종료 기록 보관 및 파기

픽업의 자동 만료 기간과 종료 후 기록 보관 기간은 별개다.

마중은 종료된 픽업과 연결된 요청 기록을 일정 기간 보관한 뒤 정리한다.

### 기본 보관 기간

**종료 또는 만료 이후 7일**

| 기록 | 보관 기간 계산 기준 |
| --- | --- |
| 완료된 픽업 | 완료 시각 |
| 취소된 픽업 | 취소 시각 |
| 만료된 픽업 | 만료 시각 |
| 픽업에 연결된 요청 | 관련 픽업의 종료 기준 |
| 픽업이 없는 취소·거절 요청 | 해당 요청의 종료 시각 |
| 미응답 요청 | 요청 만료 시각 |

### 진행 중인 요청 보호

요청 생성 시각만을 기준으로 연결된 요청을 삭제하지 않는다.

진행 중인 픽업과 연결된 요청은 해당 픽업의 종료 상태와 보관 기준을 함께 확인한다.

이를 통해 픽업이 아직 진행 중인데 요청 기록만 먼저 삭제되는 상황을 방지한다.

### 보관 정리 주기

기본 정리 주기는 하루다.

프로세스 시작 후 약 1분이 지나면 첫 보관 정리 작업을 실행한다.

따라서 보관 기간이 7일이라고 해도 종료 시각으로부터 정확히 7일이 되는 초에 기록이 삭제되는 것은 아니다.

운영 환경변수로 정리 주기를 별도로 지정한 경우에는 해당 설정을 우선 적용한다.

---

## 5. 운영 환경변수

기본 보관 기간은 다음과 같이 설정한다.

```properties
MAJUNG_RETENTION_PERIOD=P7D
```

`P7D`는 7일을 의미한다.

### 기존 설정 확인

이전 배포의 환경변수가 다음과 같이 유지되어 있다면 주의해야 한다.

```properties
MAJUNG_RETENTION_PERIOD=PT24H
```

`PT24H`는 24시간을 의미한다.

새 코드가 배포되더라도 기존 환경변수가 남아 있으면 24시간 보관 정책이 적용될 수 있다.

따라서 배포 전 운영 환경변수의 실제 값을 확인해야 한다.

**코드의 기본값 변경과 운영 환경의 실제 설정 변경은 별개의 작업이다.**

## 6. 기존 데이터베이스 반영

자동 만료와 기록 정리 기능을 운영 데이터베이스에 적용하기 전에 기존 데이터와 스키마를 확인한다.

### 적용 SQL

```text
src/main/resources/db/add-pickup-lifecycle.sql
```

### 추가 컬럼

| 테이블 | 컬럼 | 용도 |
| --- | --- | --- |
| `pickup` | `arrived_at` | 최초 도착 처리 시각 |
| `pickup` | `last_vehicle_activity_at` | 마지막 정상 차량 활동 시각 |
| `ride_request` | `ended_at` | 요청 종료 시각 |

### 마이그레이션 기준

1. 운영 데이터베이스 백업
2. 기존 스키마 및 데이터 확인
3. SQL 마이그레이션 적용
4. 신규 컬럼 및 기존 데이터 확인
5. 애플리케이션 배포
6. 운영 환경변수 확인
7. 픽업 만료 및 정리 작업 상태 확인

마이그레이션 SQL은 대상 컬럼이 이미 존재하면 중복 생성하지 않도록 작성했다.

### 기존 ARRIVED 픽업

기존 `ARRIVED` 픽업에 도착 시각이 없는 경우에만 마이그레이션 시점부터 유예 시간을 부여한다.

기존 데이터에 확인되지 않은 과거 도착 시각을 임의로 만들어 넣지 않는다.

### 기존 픽업의 만료 상한

기존 픽업의 `expires_at`을 일괄적으로 12시간으로 연장하지 않는다.

새로운 자동 만료 정책과 기존 픽업 데이터에 대한 마이그레이션 처리는 구분한다.

### 배포 주의사항

마이그레이션과 코드 배포는 각각 검증해야 한다.

애플리케이션을 이전 버전으로 되돌리더라도 적용된 데이터베이스 변경이 자동으로 복구되지는 않는다.

운영 환경에서는 [블루·그린 배포](blue-green.md)의 스키마 호환성 기준도 함께 확인한다.

## 7. 테스트 환경

**검증일: 2026년 10월 26일**

당시 최신 `main`의 다음 기능을 통합한 상태에서 검사했다.

- 초대 링크 첫 접속자 자동 연결
- 탑승자 연결 종료
- 도착 임박 알림
- 픽업 자동 만료
- 종료 기록 보관 및 정리

### 전체 테스트 결과

| 항목 | 결과 |
| --- | --- |
| 전체 서버 테스트 | 74건 |

| 수동 환경 시험 | 1건 제외 |
| `bootJar` 빌드 | 성공 |

제외된 수동 환경 시험은 통과한 테스트로 계산하지 않는다.

위 결과는 2026년 10월 26일 당시의 테스트 기록이며, 이후 모든 코드 변경의 검증 결과를 의미하지 않는다.

## 8. 자동 만료 테스트

### ACTIVE 유예 시간

다음 조건을 확인했다.

- 정상 차량 정보 수신 시 활동 시각 갱신
- 웹 조회로 활동 유예 연장되지 않음
- 준비 상태 변경으로 활동 유예 연장되지 않음
- 오래된 차량 정보로 활동 유예 연장되지 않음
- 자동 연결 이후 최초 활동 유예 적용

### ARRIVED 유예 시간

- 최초 도착 처리 시각 기록
- 중복 도착 요청으로 유예 시간 연장되지 않음
- 도착 후 차량 정보 갱신으로 유예 시간 연장되지 않음

### 전체 만료 상한

- 유효한 차량 정보가 계속 들어와도 생성 후 12시간 상한 유지
- 픽업 상태에 따라 기존 종료 상태 유지
- 반복 만료 처리로 종료 결과 변경되지 않음

### 주기 작업 및 동시 처리

- 100건을 초과하는 열린 픽업 검사
- 반복 정리 작업
- 이미 완료된 픽업의 상태 유지
- 개별 픽업 잠금 기반 처리

### 알림 구독 정리

- API 조회 과정에서 만료된 구독 정리
- 주기적 만료 작업에서 구독 정리

픽업의 종료와 연결된 알림 구독 정리를 함께 확인했다.

## 10. 검증 범위와 운영 확인
