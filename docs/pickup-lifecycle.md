# 픽업 자동 종료와 보관 기간

진행 중인 픽업을 그대로 두거나 앱이 끊긴 채 돌아오지 않는 경우를 처리한다. 탑승자 웹의 카운트다운이 0이 된 것만으로 종료하지 않는다.

| 상태 | 자동 종료 기준 |
| --- | --- |
| ACTIVE | 정상 차량 정보가 마지막으로 들어온 뒤 30분. 자동 연결 순간부터 처음 30분을 부여 |
| ARRIVED | 처음 도착 처리한 뒤 30분. 중복 도착 요청이나 새 위치로 연장하지 않음 |
| 공통 | 새 픽업 생성 후 최대 12시간 |

30분 경계에서 EXPIRED로 바꾸고 차량 위치·ETA·초대 권한을 지운다. 탑승자가 준비 상태를 바꾸거나 화면이 계속 조회해도 시간을 연장하지 않는다. 오래된 SDK 정보를 재전송하거나 명시적으로 위치를 숨기는 요청도 정상 활동으로 세지 않는다.

조회 시 만료 여부를 확인하고, 별도 작업이 1분마다 열린 픽업을 검사한다. 각 픽업을 따로 잠그며 한 번에 ID 100개씩 읽는다. EXPIRED는 웹과 차량 앱이 이미 처리하는 종료 상태다. 연결된 도착 알림 구독도 정리한다.

## 보관

종료·만료 시각부터 7일이 지난 픽업과 연결된 요청 기록을 정리한다. 픽업이 없는 취소·거절 요청은 종료 시각, 미응답 요청은 만료 시각을 기준으로 한다. 요청 생성 시각만 보고 진행 중 픽업의 요청을 먼저 지우지 않는다.

보관 정리는 기본 하루 간격이며 프로세스 시작 1분 후 첫 실행한다. 따라서 정확히 7일째 같은 초에 삭제되는 것은 아니다. 기존 배포의 환경변수로 주기를 지정했다면 그 값이 우선한다.

## 기존 DB 반영

배포 전에 백업하고 `src/main/resources/db/add-pickup-lifecycle.sql`을 실행한다. 추가 열은 `pickup.arrived_at`, `pickup.last_vehicle_activity_at`, `ride_request.ended_at`이다. SQL은 열이 있으면 다시 만들지 않으며, 기존 ARRIVED의 도착 시각이 없을 때만 이관 시점부터 유예 시간을 부여한다. 기존 픽업의 `expires_at`을 12시간으로 늘리지는 않는다.

`MAJUNG_RETENTION_PERIOD=P7D`를 사용한다. 예전 `PT24H` 환경변수가 남아 있으면 새 코드도 24시간 보관을 사용하므로 배포 전 확인한다. 새로운 종료 동작과 기존 DB 유예 처리를 구분한다.

## 시험

2026-10-26 최신 main의 자동 연결·탑승자 끊기·도착 알림을 합친 뒤 검사했다. 전체 서버 시험 74건 중 73건 통과, 수동 환경 시험 1건은 기존처럼 제외했다. bootJar 빌드도 통과했다.

- 조회·준비 상태 변경으로 30분이 연장되지 않음
- 새 정상 차량 정보만 활동 시각 갱신
- 도착 중복 요청·차량 갱신으로 도착 유예 연장되지 않음
- 차량 정보가 계속 들어와도 12시간 상한 유지
- 자동 연결 후 별도 승인 없이도 활동 유예 적용
- 100건을 넘는 검사, 반복 실행, 기존 완료 상태 유지
- 조회와 주기 작업 양쪽에서 만료된 푸시 구독 제거
- 7일 경계의 삭제와 진행 중·최근 종료 요청 보존
