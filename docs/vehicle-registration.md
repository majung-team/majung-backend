
# 차량 등록 코드 및 권한 관리

마중 백엔드의 관리자용 차량 등록, 장치 권한 확인 및 철회 절차를 설명한다.

이 문서는 **내부 시험·운영 관리자를 위한 기술 문서**다. 일반 운전자가 차량을 처음 연결하는 절차가 아니다.

일반 사용자는 차량 화면에 표시되는 QR코드를 휴대전화로 열어 카카오 로그인과 차량 연결을 진행한다.

**[일반 사용자 차량 QR 최초 연결](vehicle-enrollment.md)**

관리자 등록 코드는 내부 관리 절차로 유지하며 일반 차량 앱 화면에 노출하지 않는다.

---

## 1. 차량 등록 및 접근 권한

관리자 방식에서는 차량마다 최초 등록 시 일회용 등록 코드를 사용한다.

등록이 완료되면 차량별 접근 권한을 발급하고, 이후 픽업 생성에는 해당 권한을 사용한다.

차량 장치 권한과 개별 픽업 권한은 서로 다르다.

### 권한 구분

| 권한 | 용도 | 사용 주체 |
| --- | --- | --- |
| 관리자 키 | 등록 코드 발급·차량 권한 철회 | 내부 관리자 |
| 차량 토큰 | 등록된 차량의 접근 권한 | 차량 앱 |
| 픽업 운전자 토큰 | 개별 픽업의 운전자 작업 | 차량 앱 |
| 픽업 탑승자 토큰 | 개별 픽업 참여 및 조회 | 탑승자 |

각 권한은 지정된 API와 작업에만 사용한다.

차량 토큰을 픽업 운전자 토큰으로 대신 사용하거나, 탑승자 토큰을 차량 등록 권한으로 사용할 수 없다.

### 관리자 등록 흐름

```text
관리자
   │
   ▼
일회용 등록 코드 발급
   │
   ▼
차량에 코드 전달
   │
   ▼
차량 등록 요청
   │
   ▼
서버가 코드 검증·소비
   │
   ▼
vehicleId·vehicleToken 발급
   │
   ▼
차량 권한으로 픽업 생성
   │
   ▼
개별 픽업 driverToken 사용
```

등록 코드는 최초 등록에만 사용한다.

이미 등록된 차량의 일반적인 픽업 생성에는 관리자 코드를 다시 요구하지 않는다.

---

## 2. 관리자 인증

관리자 API는 서버에 설정한 전용 키로 보호한다.

### 환경변수

```text
MAJUNG_ADMIN_KEY
```

32자 이상의 무작위 값을 사용한다.

관리자 키는 운영 서버에서만 관리하며 다음 위치에 포함하지 않는다.

- 차량 APK
- 모바일 웹 소스 및 빌드 파일
- Git 저장소
- 공개 API 문서의 실제 요청 예시
- 로그와 시연 캡처

이전에 사용한 `MAJUNG_CREATION_KEY` 방식으로는 픽업을 생성할 수 없다.

### 인증 방식

관리자 요청은 Bearer 인증을 사용한다.

```http
Authorization: Bearer <관리자 키>
```

실제 키를 URL 쿼리 파라미터에 넣지 않는다.

관리자 API는 개인 관리 환경에서 실행하며, 모든 응답에 다음 캐시 정책을 적용한다.

```http
Cache-Control: no-store
```

---

## 3. 관리자 등록 코드 발급

### 등록 코드 생성

```http
POST /api/v1/admin/vehicle-registration-codes
```

유효한 관리자 Bearer 권한이 필요하다.

서버는 일회용 차량 등록 코드를 발급한다.

### 응답 정보

- `code`: 일회용 등록 코드
- `registrationCodeId`: 등록 코드 관리 ID
- 만료 시각

### 코드 사용 조건

| 항목 | 정책 |
| --- | --- |
| 유효 시간 | 발급 후 10분 |
| 사용 가능 횟수 | 1회 |
| 재사용 | 불가 |
| 만료 후 등록 | 불가 |
| 원본 코드 DB 저장 | 하지 않음 |

등록 코드는 유효 시간 안에 한 번만 사용할 수 있다.

등록에 성공하면 해당 코드를 소비 처리한다.

---

## 4. 차량 최초 등록

관리자가 발급한 코드를 이용해 차량을 등록한다.

### 차량 등록 API

```http
POST /api/v1/vehicles/registrations
```

요청 본문:

```json
{
  "code": "일회용 등록 코드",
  "displayName": "시험 차량"
}
```

위 값은 예시다.

### 등록 응답

등록에 성공하면 서버는 다음 정보를 발급한다.

- `vehicleId`
- `vehicleToken`

`vehicleToken` 원문은 최초 등록 응답에서 한 번만 발급한다.

서버는 이후 조회 API에서 차량 토큰 원문을 다시 제공하지 않는다.

### 차량 권한 보관

차량 앱은 발급받은 접근 권한을 암호화 저장소에 보관한다.

토큰을 일반 로그나 시연 화면에 출력하지 않는다.

차량의 등록 권한과 운전자 계정 연결은 구분하여 관리한다.

---

## 5. 차량 권한 확인

등록된 차량은 자신의 접근 권한이 유효한지 확인할 수 있다.

### API

```http
GET /api/v1/vehicles/me
```

요청에는 차량 Bearer 권한이 필요하다.

서버는 차량 권한을 확인하여 해당 차량의 정보를 반환한다.

차량 토큰 원문은 응답에 포함하지 않는다.

### 확인 대상

- 차량 등록 여부
- 현재 접근 권한의 유효성
- 차량 권한 철회 여부

다른 차량의 권한을 이용해 해당 차량 정보를 조회할 수 없도록 제한한다.

---

## 6. 차량 권한으로 픽업 생성

차량 등록이 완료되면 차량 접근 권한으로 새로운 픽업을 생성한다.

### API

```http
POST /api/v1/pickups
```

요청에는 다음 정보가 필요하다.

- 차량 Bearer 권한
- 기존 API 형식의 `place` JSON

서버는 차량 권한을 검증한 뒤 픽업을 생성한다.

### 픽업 생성 후 권한

픽업 생성 응답에는 개별 픽업 작업에 사용할 별도의 `driverToken`이 포함된다.

이후 픽업 조작은 해당 픽업의 운전자 토큰을 사용한다.

### 권한 분리

```text
vehicleToken
    │
    └── 차량 확인 및 픽업 생성

driverToken
    │
    └── 생성된 특정 픽업의 운전자 작업

passengerToken
    │
    └── 해당 픽업의 탑승자 작업
```

차량 권한이 있다고 해서 임의의 다른 픽업에 접근할 수 있는 것은 아니다.

개별 픽업 권한은 해당 픽업의 상태 및 접근 범위에 따라 검증한다.

---

## 7. 등록 응답 유실 및 재시도

차량 등록 요청을 보낸 뒤 네트워크 오류로 응답을 받지 못할 수 있다.

이때 동일한 등록 코드를 자동으로 재전송하지 않는다.

서버에서는 해당 코드가 이미 사용됐을 가능성이 있기 때문이다.

### 관리자 코드 상태 조회

```http
GET /api/v1/admin/vehicle-registration-codes/{registrationCodeId}
```

관리자는 이 API로 다음 정보를 확인한다.

- 등록 코드 사용 여부
- 등록 결과
- 발급된 `vehicleId`

조회 응답에는 등록 코드 원문이나 차량 토큰 원문을 포함하지 않는다.

### 복구 절차

1. 차량 등록 응답 유실 확인
2. 동일 코드의 자동 재시도 중단
3. 관리자가 코드 사용 여부 조회
4. 등록된 차량이 있다면 `vehicleId` 확인
5. 필요하면 기존 차량 권한 철회
6. 새로운 일회용 등록 코드 발급
7. 차량 재등록 진행

등록 응답을 잃었다는 이유만으로 서버에 차량이 생성되지 않았다고 가정하지 않는다.

---

## 8. 차량 권한 철회

관리자는 특정 차량의 접근 권한을 철회할 수 있다.

### API

```http
POST /api/v1/admin/vehicles/{vehicleId}/revocation
```

관리자 Bearer 권한이 필요하다.

### 철회 시 처리

차량 권한을 철회하면 다음 작업이 수행된다.

- 해당 차량의 접근 권한 무효화
- 해당 차량의 진행 중 픽업 취소
- 저장된 차량 위치 및 ETA 즉시 제거
- 철회된 차량의 신규 픽업 생성 차단

다른 차량의 등록 상태 및 접근 권한에는 영향을 주지 않는다.

### 반복 철회

동일 차량에 철회 요청을 반복하더라도 같은 결과를 반환하도록 처리한다.

중복 철회로 다른 차량이나 픽업에 영향을 주지 않는다.

### 재등록

철회된 차량을 다시 사용하려면 새 등록 코드를 발급받아 등록해야 한다.

기존 차량 토큰을 다시 활성화하지 않는다.

---

## 9. 오류 코드

관리자·차량 등록 및 접근 권한 처리에서 사용하는 주요 오류 코드다.

| 오류 코드 | 의미 | 대응 |
| --- | --- | --- |
| `REGISTRATION_CODE_UNAVAILABLE` | 등록 코드가 만료·소비됐거나 존재하지 않음 | 관리자가 새 코드 발급 |
| `VEHICLE_REGISTRATION_REQUIRED` | 차량 최초 등록 필요 | 차량 등록 절차 진행 |
| `VEHICLE_CREDENTIAL_INVALID` | 차량 권한 불일치 | 관리자 확인 후 재등록 |
| `VEHICLE_REVOKED` | 차량 권한 철회됨 | 새 픽업 생성 중단 및 재등록 |
| `ADMIN_REQUIRED` | 유효한 관리자 인증 필요 | 관리자 인증 확인 |
| `ADMIN_DISABLED` | 관리자 기능 비활성 상태 | 서버 설정 확인 |
| `RETRY_REQUEST` | 동시 처리 충돌 | 현재 상태 확인 후 재요청 |

오류가 발생했을 때 무조건 같은 요청을 반복하지 않는다.

특히 등록 코드 소비 여부와 차량 생성 여부를 확인해야 하는 경우에는 관리자 상태 조회를 우선한다.

---

## 10. 토큰 및 등록 코드 보안

### 서버 저장 방식

서버 데이터베이스에는 다음 비밀 값의 SHA-256 해시만 보관한다.

- 차량 등록 코드
- 차량 접근 권한

원본 코드나 차량 토큰을 데이터베이스에서 다시 읽어 사용자에게 제공하지 않는다.

### 권한 사용 제한

관리자 키, 차량 토큰, 픽업 운전자 토큰, 탑승자 토큰은 서로 다른 용도로 사용한다.

다른 종류의 토큰을 대신 제출하더라도 권한을 부여하지 않는다.

### 민감 정보 관리

다음 정보는 저장소·로그·공개 문서에 포함하지 않는다.

- 관리자 키 원문
- 일회용 등록 코드 원문
- 차량 토큰 원문
- 픽업 접근 토큰
- 실제 사용자 위치 및 개인정보

API 예시는 실제 운영 비밀 값이 아닌 임의의 예시 값만 사용한다.

---

## 11. 개발 모드와 운영 모드

로컬 개발과 운영 배포는 서로 다른 보안 조건을 적용한다.

### 로컬 개발 모드

```properties
developmentToolsEnabled=true
```

해당 설정이 활성화된 로컬 개발 환경에서만 등록되지 않은 차량의 픽업 생성이 허용될 수 있다.

개발 편의를 위한 제한적인 설정이다.

### 운영 배포 모드

`deploy` 프로필에서는 개발 도구 기능을 비활성화한다.

또한 다음 항목을 필수로 검사한다.

- 관리자 키 설정
- 요청 제한 설정
- 보관 및 정리 설정
- 차량 접근 권한

운영 환경에서 개발 모드로 등록 검증을 우회하지 않는다.

---

## 12. 데이터베이스 초기화 및 업그레이드

신규 환경과 기존 운영 환경은 서로 다른 SQL을 사용한다.

### 신규 데이터베이스

```text
src/main/resources/db/initial-schema.sql
```

신규 DB에서는 초기 스키마를 한 번 적용한다.

### 기존 데이터베이스

기존 운영 DB에는 다음 업그레이드 SQL을 사용한다.

```text
db/upgrade-vehicle-registration.sql
```

### 적용 순서

1. 기존 API 중지
2. 운영 PostgreSQL 백업
3. 업그레이드 SQL 확인
4. 스키마 변경 적용
5. 새 JAR 배포
6. DB 접근 권한 및 실행 상태 확인
7. 차량 등록 API 확인

기존 DB 업그레이드 SQL은 해당 환경에 한 번 적용하는 절차다.

반복 실행 가능 여부를 확인하지 않고 재적용하지 않는다.

### 기존 픽업 처리

이전 버전에서 생성한 픽업은 `vehicleId`가 없을 수 있다.

이러한 기존 픽업은 원래 만료 및 종료 정책을 따른다.

과거 픽업을 임의의 차량에 연결하지 않는다.

---

## 13. 데이터베이스 스키마 관리

로컬 개발과 운영 환경에서 서로 다른 JPA 스키마 관리 정책을 사용한다.

| 환경 | 스키마 처리 |
| --- | --- |
| 로컬 H2 개발 | `update` 모드 사용 가능 |
| 운영 PostgreSQL | `validate` 모드 |

운영 데이터베이스에 자동 스키마 변경을 활성화하지 않는다.

DB 구조 변경은 명시적인 SQL과 배포 절차로 관리한다.

기존 애플리케이션으로 복구해야 하는 경우 스키마 호환성도 함께 확인한다.

---

## 14. 테스트 및 검증

차량 등록과 권한 철회는 실제 HTTP 요청을 사용하는 테스트로 검증한다.

### 등록 코드

- 등록 코드 만료
- 사용 완료 코드의 재사용 차단
- 동시에 같은 코드를 소비하는 요청 처리
- 잘못된 코드 접근 차단

### 차량 등록 및 픽업 생성

- 미등록 차량의 픽업 생성 차단
- 등록 성공 후 반복 픽업 생성
- 차량 토큰과 픽업 토큰의 용도 분리
- 차량 등록 상태 확인

### 차량 권한 철회

- 개별 차량 권한 철회
- 다른 차량에 영향이 없는지 확인
- 진행 중인 픽업 취소
- 저장된 위치·ETA 삭제
- 반복 철회 처리

### 데이터베이스

초기 SQL을 사용한 배포 데이터베이스 스키마 검증을 수행한다.

### 검증 범위 구분

위 항목은 서버의 실제 HTTP 테스트 기준이다.

다음 항목은 별도 실행 기록이 필요하다.

- 실제 GCP 운영 서버 반영
- 차량 APK와 운영 API 연동
- 실제 휴대전화와의 전체 연결 흐름
- 실차 환경에서의 차량 권한 관리

서버 테스트 통과만으로 운영 반영 또는 실제 기기 연동까지 완료됐다고 기록하지 않는다.

## 15. 일반 사용자 연결과의 차이

| 항목 | 일반 사용자 QR 최초 연결 | 내부 관리자 등록 |
| --- | --- | --- |
| 대상 | 일반 운전자 | 내부 시험·관리자 |
| 시작 방법 | 차량 QR | 관리자 일회용 코드 |
| 카카오 로그인 | 사용 | 등록 코드 발급 자체에는 불필요 |
| 차량 최종 승인 | 필요 | 관리자 등록 절차에 따름 |
| 관리자 키 | 필요 없음 | 필요 |
| 차량 토큰 발급 | 최초 연결 과정 | 등록 API 응답 |
| 관련 문서 | [차량 QR 최초 연결](vehicle-enrollment.md) | 현재 문서 |

일반 사용자의 최초 연결은 QR 기반 방식으로 안내한다.

관리자 등록 코드는 운영 관리 및 내부 시험 기능으로 구분하여 유지한다.

## 문서 관리 기준

이 문서는 내부 관리자 등록 코드 기반의 차량 최초 등록과 권한 철회 절차를 설명한다.

일반 사용자 QR 연결과 내부 관리자 등록을 구분하고, 관리자 키·차량 토큰·픽업 운전자 토큰·탑승자 토큰을 각각 별도의 권한으로 관리한다.

등록 응답 유실, 코드 중복 사용, 차량 권한 철회 등 보안과 데이터 정합성에 영향을 주는 동작은 실제 서버 테스트 결과를 기준으로 기록한다.

운영 DB 변경, GCP 배포 및 실차 검증은 별도의 근거가 있을 때만 완료로 표시한다.
