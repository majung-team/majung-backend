
# 픽업 장소 변경 제안

마중은 진행 중인 픽업에서 탑승자 또는 운전자가 기존 약속 장소와 다른 장소를 제안할 수 있도록 지원한다.

장소 변경은 **제안 등록과 실제 장소 확정**을 분리하여 처리한다.

- **기능 6.1 — 장소 제안:** 서버에 새로운 장소 제안을 저장하거나 취소한다.
- **기능 6.2 — 장소 확정:** 차량 앱에서 제안을 확인하고 내비게이션 경로를 검증한 뒤 장소 변경을 확정한다.

이 문서는 기능 6.1의 API, 접근 권한, 상태 처리, 데이터베이스 변경 및 검증 결과를 설명한다.

> 장소 제안 API를 호출해도 기존 확정 장소는 변경되지 않는다. 경로 요청과 최종 장소 확정은 차량 앱의 별도 승인 흐름에서 처리한다.

---

## 1. 기능 개요

| 항목 | 정책 |
| --- | --- |
| 제안 가능 사용자 | 해당 픽업의 운전자 또는 연결된 탑승자 |
| 제안 가능 상태 | `ACTIVE` |
| 동시 보관 제안 | 픽업당 1개 |
| 새 제안 등록 | 기존 제안 대체 |
| 제안 삭제 | 운전자 또는 제안한 탑승자 |
| 확정 장소 변경 | 제안 API에서는 수행하지 않음 |
| 내비게이션 경로 변경 | 차량 앱의 별도 검증·승인 절차 |
| 보관 기간 | 픽업 종료 후 보관 정책에 따라 정리 |

### 기본 흐름

1. 운전자 또는 탑승자가 지도에서 다른 장소를 선택한다.
2. 서버에 장소 변경 제안을 등록한다.
3. 기존 확정 장소는 그대로 유지한다.
4. 차량 앱에서 제안된 장소를 확인한다.
5. 차량이 내비게이션 SDK로 새 경로를 검증한다.
6. 운전자가 장소 변경을 승인한다.
7. 별도 확정 처리에서 새로운 장소를 반영한다.

제안 등록만으로 경로를 변경하거나 새로운 ETA를 확정하지 않는다.

---

## 2. 장소 제안과 확정 장소의 구분

픽업에는 현재 확정된 장소인 `place`와 변경 요청인 `placeProposal`이 존재할 수 있다.

| 필드 | 의미 | 변경 기준 |
| --- | --- | --- |
| `place` | 현재 확정된 픽업 장소 | 차량 승인 및 확정 처리 |
| `placeProposal` | 운전자 또는 탑승자가 제안한 장소 | 제안 등록·삭제 |
| `proposedBy` | 제안자 구분 | 제안 등록 시 기록 |
| `proposedAt` | 제안 시각 | 제안 등록 시 기록 |

`placeProposal`이 존재해도 `place`는 기존 확정 장소를 유지한다.

### 응답 예시

```json
{
  "place": {
    "label": "예시 장소",
    "latitude": 37.0,
    "longitude": 127.0
  },
  "placeProposal": {
    "place": {
      "label": "정문 앞",
      "latitude": 37.001,
      "longitude": 127.002
    },
    "proposedBy": "PASSENGER",
    "proposedAt": "2026-10-26T05:00:00Z"
  }
}
```

위 응답에서는 `정문 앞`이 새로운 제안 장소이지만, 아직 확정된 픽업 장소는 `예시 장소`다.

제안이 없으면 `placeProposal`은 `null`이다.

### 제안자 구분

| 값 | 의미 |
| --- | --- |
| `DRIVER` | 운전자 제안 |
| `PASSENGER` | 탑승자 제안 |

제안자를 기록하여 제안 삭제 권한을 구분한다.

## 3. 초대 기반 픽업 API

운전자 토큰 또는 연결된 탑승자 토큰을 사용한다.

| Method | API | 기능 |
| --- | --- | --- |
| `PUT` | `/api/v1/pickups/{id}/place-proposal` | 장소 제안 등록·교체 |
| `DELETE` | `/api/v1/pickups/{id}/place-proposal` | 장소 제안 삭제 |
| `GET` | `/api/v1/pickups/{id}` | 확정 장소 및 현재 제안 조회 |

### 장소 제안 등록

```http
PUT /api/v1/pickups/{id}/place-proposal
Content-Type: application/json
```

요청 예시:

```json
{
  "place": {
    "label": "정문 앞",
    "latitude": 37.001,
    "longitude": 127.002
  }
}
```

서버는 권한과 픽업 상태를 확인한 뒤 새로운 제안을 저장한다.

이미 제안이 있으면 새 제안으로 대체한다.

이때 기존 `place`는 변경하지 않는다.

### 장소 제안 삭제

```http
DELETE /api/v1/pickups/{id}/place-proposal
```

현재 제안을 삭제한다.

삭제할 제안이 없더라도 HTTP 200을 반환한다.

제안 삭제는 확정된 픽업 장소를 변경하는 작업이 아니다.

### 픽업 조회

```http
GET /api/v1/pickups/{id}
```

응답에는 확정 장소와 현재 제안 정보가 포함된다.

제안이 없으면 `placeProposal`은 `null`이다.

## 4. 마중 요청 기반 픽업 API

운전자 검색 후 시작된 마중 요청 기반 픽업에도 같은 장소 제안 기능을 제공한다.

| Method | API | 권한 |
| --- | --- | --- |
| `PUT` | `/api/v1/ride-requests/{id}/place-proposal` | 로그인한 해당 탑승자 |
| `DELETE` | `/api/v1/ride-requests/{id}/place-proposal` | 로그인한 해당 탑승자 |

마중 요청 기반 API는 웹 로그인 세션을 사용한다.

상태를 변경하는 요청에는 CSRF 검증이 필요하다.

해당 요청으로 시작된 자신의 픽업에 대해서만 장소를 제안하거나 허용된 범위에서 삭제할 수 있다.

다른 사용자의 요청이나 다른 픽업의 장소 제안에 접근할 수 없다.

초대 기반 픽업과 요청 기반 픽업은 인증 방식이 다르지만 장소 제안 정책은 공유한다.

## 5. 장소 제안 규칙

### 제안은 하나만 유지

픽업당 한 번에 하나의 제안만 저장한다.

새로운 제안이 등록되면 이전 제안을 대체한다.

제안자와 제안 시각도 새 제안을 기준으로 갱신한다.

### 확정 장소와 동일한 위치 제한

현재 확정 장소와 사실상 같은 좌표를 다시 제안할 수 없다.

약 1m 이내의 동일한 장소로 판단되면 다음 오류를 반환한다.

```text
409 SAME_PLACE
```

이는 제안 장소와 현재 확정 장소의 중복을 막기 위한 기준이다.

### 제안과 경로의 독립성

제안을 저장했다고 해서 다음 동작을 수행하지 않는다.

- 확정 장소 변경
- 내비게이션 목적지 변경
- 경유지 자동 추가
- 기존 ETA 무효화 또는 새 ETA 확정
- 픽업 상태 자동 변경

경로 검증과 실제 장소 확정은 별도 처리한다.

---

## 6. 제안 삭제 권한

제안 삭제 권한은 제안자와 운전자 여부에 따라 결정한다.

| 요청자 | 운전자 제안 삭제 | 탑승자 제안 삭제 |
| --- | --- | --- |
| 해당 픽업 운전자 | 가능 | 가능 |
| 해당 픽업 탑승자 | 불가 | 본인 제안만 가능 |
| 관련 없는 사용자 | 불가 | 불가 |

### 운전자

운전자는 현재 픽업의 제안이 누구에게서 생성됐는지와 관계없이 삭제할 수 있다.

### 탑승자

탑승자는 자신이 등록한 제안만 삭제할 수 있다.

운전자가 등록한 제안을 탑승자가 삭제하려 하면 HTTP 403을 반환한다.

제안 삭제 권한이 없다는 이유로 기존 픽업의 확정 장소나 상태를 변경하지 않는다.

## 7. 픽업 상태별 처리

장소 제안은 픽업의 진행 상태에 따라 제한한다.

| 픽업 상태 | 제안 등록 | 제안 삭제 |
| --- | --- | --- |
| 연결 전 | 불가 · HTTP 403 | 권한 정책에 따름 |
| `ACTIVE` | 가능 | 가능 |
| `ARRIVED` | 불가 · `INVALID_STATE` | 가능 |
| 완료·취소·만료 | 불가 · HTTP 410 | 종료 상태 접근 정책에 따름 |

### ACTIVE

진행 중인 픽업에 한해 새로운 장소를 제안할 수 있다.

### ARRIVED

차량이 이미 도착 처리된 뒤에는 새로운 장소 제안을 등록할 수 없다.

```text
409 INVALID_STATE
```

다만 기존 제안을 삭제하는 것은 허용한다.

### 종료된 픽업

완료·취소·만료된 픽업에는 새로운 장소를 제안할 수 없다.

HTTP 410으로 종료 상태를 알린다.

종료된 픽업의 조회 응답에서는 기존 장소 제안을 숨긴다.

---

## 8. 탑승자 연결 변경

장소 제안은 현재 픽업에 연결된 탑승자와 관련된 정보다.

따라서 다음 상황에서는 기존 제안을 삭제한다.

- 현재 탑승자의 연결 종료
- 새로운 탑승자 연결

이전 탑승자가 남긴 장소 제안을 다음 탑승자의 제안처럼 유지하지 않는다.

탑승자 연결과 픽업 접근 권한이 변경되면 제안 정보의 유효성도 함께 정리한다.

---

## 9. 데이터 저장 및 보관

장소 제안은 별도 제안 테이블이 아니라 `pickup` 테이블에 저장한다.

### 저장 위치

```text
pickup.proposal_*
```

제안 장소, 제안자 및 제안 시각에 필요한 컬럼을 사용한다.

제안이 없으면 관련 컬럼은 `NULL`일 수 있다.

### 보관 기간

장소 제안 데이터는 해당 픽업과 함께 보관된다.

픽업 종료 후 기본 7일 보관 정책에 따라 관련 데이터가 정리된다.

별도의 장소 제안 영구 보관 기간을 두지 않는다.

[픽업 자동 종료 및 보관 정책](pickup-lifecycle.md)

## 10. 데이터베이스 마이그레이션

기존 데이터베이스에는 `pickup` 테이블의 장소 제안 컬럼을 추가해야 한다.

### 적용 SQL

```text
src/main/resources/db/add-place-proposal.sql
```

실행 예시:

```sh
psql -f src/main/resources/db/add-place-proposal.sql
```

위 명령은 PostgreSQL 접속 환경이 준비된 경우의 예시다.

운영 데이터베이스에는 백업과 대상 DB 확인 후 적용한다.

### 변경 특성

- 기존 `pickup` 테이블에 컬럼 추가
- 추가 컬럼은 `NULL` 허용
- `IF NOT EXISTS` 사용
- 기존 데이터 유지
- 이전 서버 코드와 호환
- 기존 `pickup` 테이블의 `UPDATE` 권한 재사용

컬럼 추가 SQL은 반복 적용을 고려해 작성했다.

다만 실제 운영에서는 마이그레이션 이력을 확인하고 중복 실행이 필요한지 판단한다.

### 적용 순서

1. 운영 PostgreSQL 백업
2. 대상 데이터베이스 확인
3. 장소 제안 SQL 적용
4. 새 컬럼 생성 여부 확인
5. 신규 서버 배포
6. 장소 제안 API 확인
7. 차량 및 모바일 웹 연동 확인

### 배포 순서가 중요한 이유

배포 프로필은 서버 시작 시 데이터베이스 구조를 검사한다.

따라서 **신규 서버 JAR를 실행하기 전에 장소 제안 컬럼이 준비되어 있어야 한다.**

해당 컬럼이 없는 상태에서 새 버전을 배포하면 서버 기동 검증에 실패할 수 있다.

## 11. 준비 상태와의 독립성

장소 제안은 탑승자 준비 상태와 별개의 데이터다.

다음 정보가 서로 영향을 주지 않도록 처리한다.

- 현재 확정 장소
- 장소 변경 제안
- 탑승자 준비 상태
- 준비 상태 수신 확인

### 준비 상태 수신 확인

준비 상태 수신 확인 작업을 수행해도 장소 제안과 확정 장소가 변경되지 않는다.

### 제안 취소

장소 제안을 취소하더라도 기존 준비 상태와 수신 확인 정보는 유지한다.

장소 제안 기능을 추가하면서 기존 픽업 상태나 준비 상태 처리가 변경되지 않도록 회귀 테스트를 수행했다.

- 픽업 자동 종료
- 종료 기록 7일 보관

### 서버 테스트 결과

| 항목 | 결과 |
| --- | --- |

### 주요 HTTP 회귀 테스트

다음 항목을 확인했다.

- 장소 제안 저장
- 제안 취소
- 준비 상태 수신 확인 시 제안 유지
- 준비 상태 수신 확인 시 확정 장소 유지
- 제안 삭제 후 준비 상태 유지
- 제안 삭제 후 수신 확인 정보 유지

장소 제안 기능이 기존 준비 상태 처리에 영향을 주지 않는지 확인했다.

## 13. 로컬 브라우저 통합 검증

실제 로컬 Spring 서버와 Spring Security, 가상 로그인 공급자를 이용해 브라우저 연동을 확인했다.

### 시험 구성

- 로컬 Spring Boot 서버
- 실제 Spring Security 인증 처리
- 가상 로그인 계정
- 실제 지도 SDK
- 계정 웹 화면

### 확인한 흐름

1. 가상 계정 로그인
2. 계정 화면에서 장소 선택
3. 장소 제안 등록
4. 서버 제안 상태 확인
5. 장소 제안 취소
6. 기존 확정 장소 유지 확인

이는 단순 Mock API 시험과 구분되는 로컬 브라우저 통합 시험이다.

다만 실제 카카오 계정이나 공개 운영 서버를 이용한 시험은 아니다.

## 14. 2026년 10월 26일 당시 배포 상태

해당 통합 검증을 수행한 시점에는 운영 데이터베이스의 장소 제안 컬럼과 배포 허용 목록이 아직 이 기능에 맞게 변경되지 않았다.

따라서 당시 시험 통과만으로 운영 서버에 장소 제안 기능이 배포됐다고 판단하지 않는다.

또한 다음 기능은 별도 연동 범위였다.

- 차량에서 제안 확인
- 내비게이션 SDK의 새 경로 검증
- 운전자의 최종 승인
- 확정 장소 변경

이 기록은 **2026년 10월 26일 당시의 구현·검증·배포 상태**다.

이후 운영 반영 여부와 기능 6.2의 검증 결과는 최신 배포 커밋과 개발 현황을 기준으로 확인한다.

## 15. 기능 경계 및 검증하지 않은 범위

### 이번 문서에서 확인한 기능

- 운전자·탑승자 장소 제안
- 제안 한 건 유지 및 교체
- 제안 삭제 권한 구분
- 확정 장소 유지
- 준비 상태와의 독립성
- 로컬 서버·브라우저 통합 흐름

### 별도 확인이 필요한 기능

- 실제 차량의 제안 승인
- Pleos NaviHelper SDK의 새 경로 검증
- 차량 경로 변경 후 ETA 무효화·재수신
- 장소 확정 API의 상태 전이
- 운영 DB 마이그레이션
- 공개 HTTPS에서의 전체 연동
- 실제 휴대전화 및 실차 시험

제안 API 테스트와 차량의 실제 경로 변경 성공을 같은 검증 결과로 기록하지 않는다.

이 문서는 기능 6.1의 장소 제안 API와 2026년 10월 26일 통합 검증 결과를 기록한다.
