
# 도착 임박 웹 푸시 알림

마중은 차량이 탑승자의 픽업 장소에 약 3분 이내로 접근하면 웹 푸시 알림을 발송한다.

탑승자가 브라우저 화면을 닫거나 다른 앱을 사용하는 동안에도 브라우저와 운영체제가 허용하는 조건에서 알림을 받을 수 있다.

푸시 구독은 개별 픽업에 연결되며, 픽업이 종료되거나 탑승자의 접근 권한이 해제되면 함께 정리한다.

이 문서는 기능 7.1의 발송 조건, API, 보안 정책, 운영 설정 및 검증 결과를 설명한다.

> 서버에 VAPID 키가 설정되지 않으면 푸시 기능은 비활성화된다. 기존 픽업 생성, 위치·ETA 공유 및 준비 상태 처리에는 영향을 주지 않는다.

---

## 1. 기능 개요

| 항목 | 정책 |
| --- | --- |
| 발송 조건 | 활성 픽업의 ETA가 180초 이하 |
| 기본 임계값 | 3분 |
| 발송 횟수 | 픽업당 최대 한 번 시도 |
| 구독 범위 | 픽업당 하나의 구독 |
| 알림 유효 시간 | TTL 10분 |
| 발송 방식 | DB 커밋 후 비동기 처리 |
| 발송 실패 | 자동 재시도 없음 |
| 알림 내용 | 브라우저 서비스 워커에 고정 |
| VAPID 미설정 | 기능 비활성화 |

### 사용자 흐름

1. 탑승자가 픽업에 참여한다.
2. 브라우저에서 알림 권한을 허용한다.
3. 웹 푸시 구독을 생성한다.
4. 구독 주소를 서버에 등록한다.
5. 차량이 최신 위치·ETA를 전송한다.
6. 서버가 도착 임박 조건을 확인한다.
7. 발송 대상으로 확정한 뒤 비동기 발송한다.
8. 브라우저 서비스 워커가 알림을 표시한다.

실제 알림 표시는 브라우저, 운영체제, 사용자 권한 및 푸시 서비스 상태에 영향을 받는다.

서버가 발송을 시도했다는 사실과 사용자의 기기에 알림이 표시됐다는 사실은 구분한다.

---

## 2. 발송 조건

차량 정보가 갱신될 때 서버는 도착 임박 알림의 발송 조건을 확인한다.

### 기본 조건

- 픽업 상태가 `ACTIVE`
- 해당 픽업의 유효한 푸시 구독 존재
- 차량 정보에 `durationSeconds`가 존재
- `durationSeconds`가 설정된 임계값 이하
- 해당 픽업에 이전 발송 시도 기록이 없음

기본 임계값은 180초다.

```properties
majung.push.arrival-seconds=180
```

### 예시

| 차량 ETA | 결과 |
| --- | --- |
| 400초 | 발송하지 않음 |
| 181초 | 발송하지 않음 |
| 180초 | 발송 조건 충족 |
| 120초 | 미발송 픽업이라면 발송 조건 충족 |
| 이미 발송 대상으로 기록된 픽업 | 재발송하지 않음 |

ETA가 3분 이내로 진입한 뒤 구독을 다시 생성하더라도 이미 발송 처리된 픽업에는 재발송하지 않는다.

### 실제 도착과의 구분

도착 임박 푸시는 ETA 기준의 사전 안내다.

알림을 발송했다고 해서 서버가 픽업을 `ARRIVED` 상태로 변경하지 않는다.

실제 도착 처리는 별도의 픽업 상태 전이를 따른다.

## 3. 중복 발송 방지

마중은 DB의 `notified_at`을 사용해 픽업별 발송 여부를 관리한다.

### 조건부 갱신

발송 조건을 만족하면 DB에서 아직 알림 처리 기록이 없는 경우에만 `notified_at`을 기록한다.

동시에 여러 차량 정보 갱신이 들어오더라도 같은 픽업에서 중복 발송 작업이 시작되지 않도록 한다.

### 처리 흐름

```text
차량 위치·ETA 갱신
         │
         ▼
   ACTIVE 상태 확인
         │
         ▼
    ETA 180초 이하?
         │
    ┌────┴────┐
    │         │
   아니요      예
    │         │
    ▼         ▼
   종료    구독·발송 기록 확인
                  │
                  ▼
           DB 조건부 갱신
                  │
           ┌──────┴──────┐
           │             │
         성공           대상 아님
           │             │
           ▼             ▼
        DB 커밋          종료
           │
           ▼
       비동기 발송
           │
           ▼
       푸시 서비스 응답
```

### 보장 범위

이 방식은 같은 픽업에서 발송 작업이 중복 시작되는 것을 방지한다.

하지만 푸시 서비스에 실제로 전달되기 전에 장애가 발생하거나 전송에 실패할 수 있다.

발송 실패 후 자동 재시도하지 않으므로 알림 수신을 반드시 보장하지 않는다.

따라서 정책은 **픽업당 최대 한 번의 발송 시도**로 설명한다.

## 4. 비동기 발송

발송 대상 기록은 데이터베이스 트랜잭션이 커밋된 이후 처리한다.

실제 푸시 서비스 요청은 별도 스레드에서 수행한다.

### 비동기 처리 목적

- 차량 정보 저장 응답 지연 방지
- 외부 푸시 서비스 응답 지연과 분리
- 차량 위치·ETA 갱신 흐름 보호

푸시 서비스가 느리거나 응답하지 않더라도 차량 정보 전송 작업이 해당 외부 요청을 기다리지 않도록 한다.

### 실패 처리

발송 실패 시 자동 재시도하지 않는다.

알림의 TTL은 10분으로 설정한다.

TTL은 푸시 서비스가 메시지를 보관할 수 있는 유효 기간이며, 브라우저 알림이 반드시 10분 안에 표시된다는 의미는 아니다.

### 무효한 구독 정리

푸시 서비스가 다음 상태를 반환하면 구독을 삭제한다.

- HTTP 404
- HTTP 410

유효하지 않은 구독 주소로 이후 요청을 반복하지 않도록 한다.

HTTP 500 등 일시적인 서버 오류는 기록하되 이번 발송을 자동으로 재시도하지 않는다.

## 5. 개인정보 보호

도착 임박 푸시 요청에는 사용자에게 표시할 메시지 본문을 포함하지 않는다.

알림의 제목과 문구는 웹 서비스 워커에 고정되어 있다.

### 푸시 서비스로 전달하지 않는 정보

- 탑승자 이름
- 운전자 이름
- 마중 ID
- 차량 위치 좌표
- 픽업 장소
- ETA 원문
- 픽업 접근 토큰

푸시 서비스가 알림 내용을 전달하는 과정에서 이러한 개인정보를 받지 않도록 구성한다.

### 빈 페이로드

현재 구현은 빈 푸시 페이로드를 사용하므로 사용자 알림 내용을 암호화하여 전송하는 과정이 필요하지 않다.

다만 VAPID를 이용한 발신자 인증과 HTTPS 전송 등 Web Push의 기본 보안 요구사항은 그대로 적용한다.

추후 푸시 본문에 데이터를 포함할 경우에는 Web Push 페이로드 암호화와 개인정보 공개 범위를 별도로 검토해야 한다.

## 6. 푸시 구독 API

마중은 초대 기반 픽업과 로그인 계정 기반 픽업에 서로 다른 구독 API를 제공한다.

### 초대 기반 픽업

| Method | API | 인증 |
| --- | --- | --- |
| `PUT` | `/api/v1/pickups/{id}/arrival-push` | 탑승자 토큰 |
| `DELETE` | `/api/v1/pickups/{id}/arrival-push` | 탑승자 토큰 |

구독 요청 예시:

```http
PUT /api/v1/pickups/{id}/arrival-push
Content-Type: application/json
```

```json
{
  "endpoint": "https://fcm.googleapis.com/..."
}
```

구독 성공 응답:

```json
{
  "subscribed": true
}
```

구독 해제 응답:

```json
{
  "subscribed": false
}
```

### 마중 요청 기반 픽업

| Method | API | 인증 |
| --- | --- | --- |
| `PUT` | `/api/v1/ride-requests/{id}/arrival-push` | 로그인 세션·CSRF |
| `DELETE` | `/api/v1/ride-requests/{id}/arrival-push` | 로그인 세션·CSRF |

해당 요청이 실제 픽업으로 시작된 후 본인에게 허용된 픽업에만 구독을 등록할 수 있다.

### 공개 푸시 설정

```http
GET /api/v1/config
```

응답의 `webPushPublicKey`를 이용해 브라우저가 푸시 구독을 생성한다.

| 서버 상태 | `webPushPublicKey` |
| --- | --- |
| VAPID 설정 완료 | 공개 키 |
| VAPID 미설정 | `null` |

VAPID 공개 키는 브라우저에 제공해도 되는 정보다.

개인 키는 서버에만 보관한다.

---

## 7. 구독 API 오류

| HTTP 상태 | 오류 코드 | 의미 |
| --- | --- | --- |
| `400` | `INVALID_PUSH_ENDPOINT` | 허용하지 않는 구독 주소 |
| `403` | — | 탑승자 권한이 없거나 위치 공유 대상이 아님 |
| `404` | `PUSH_DISABLED` | VAPID 미설정으로 푸시 기능 비활성화 |

구독 주소의 형식뿐 아니라 픽업 참여 권한도 확인한다.

구독 API가 성공했다고 해서 브라우저와 운영체제의 알림 표시 권한까지 확인됐다는 뜻은 아니다.

## 8. 푸시 endpoint 보안

서버는 브라우저가 제출한 구독 주소로 직접 HTTPS 요청을 전송한다.

임의의 URL을 허용하면 내부 서버나 예기치 않은 외부 주소로 요청을 보내는 문제가 발생할 수 있으므로 목적지를 제한한다.

### 허용 조건

- HTTPS 사용
- 포트 443
- 허용된 푸시 서비스 호스트
- 리다이렉트 추적 금지

### 허용 서비스

| 서비스 | 허용 호스트 |
| --- | --- |
| Chrome·Android | `fcm.googleapis.com` |
| Firefox | `push.services.mozilla.com` |
| Safari·홈 화면 웹앱 | `push.apple.com` |
| Windows | `notify.windows.com` |

서버는 내부 네트워크 주소나 임의의 외부 서버를 가리키는 구독 주소를 허용하지 않는다.

푸시 서비스가 리다이렉트를 반환해도 이를 따라가지 않는다.

해당 호스트 목록은 현재 구현의 허용 정책이며, 실제 브라우저별 구독 endpoint와의 호환성은 개별적으로 검증해야 한다.

## 9. 구독 저장 및 정리

서버는 픽업 하나에 구독 주소 하나를 저장한다.

### 구독 등록

유효한 픽업 참여자만 구독을 등록할 수 있다.

새 구독이 등록되더라도 이미 알림을 발송 대상으로 처리한 픽업은 다시 알림을 보내지 않는다.

### 구독 삭제 조건

다음 상황에서는 연결된 구독을 정리한다.

- 탑승자 연결 종료
- 초대 재발급
- 픽업 완료
- 픽업 취소
- 픽업 만료
- 데이터 보관 기간 경과
- 탑승자의 명시적 구독 해제
- 푸시 서비스의 404·410 응답

### 다른 탑승자에게 알림이 전달되지 않도록 처리

이전 탑승자의 연결이 종료되면 해당 구독을 제거한다.

새로운 탑승자가 같은 픽업에 참여하더라도 이전 탑승자의 브라우저가 알림을 받지 않도록 한다.

픽업 접근 권한과 알림 구독의 생명주기를 함께 관리한다.

## 10. VAPID 키 생성

웹 푸시 기능을 활성화하려면 VAPID 키가 필요하다.

### 키 생성 명령

```sh
java deploy/VapidKeys.java
```

생성 결과:

| 항목 | 형식 |
| --- | --- |
| 공개 키 | URL-safe Base64 · 87자 |
| 개인 키 | URL-safe Base64 · 43자 |

공개 키는 브라우저의 구독 생성에 사용한다.

개인 키는 서버에서 푸시 요청을 인증하는 데 사용한다.

### 키 관리

VAPID 개인 키는 다음 위치에 포함하지 않는다.

- Git 저장소
- 공개 문서
- 차량 APK
- 웹 정적 파일
- GitHub Actions 로그
- 시연 캡처

생성한 개인 키는 운영 서버에서만 안전하게 관리한다.

## 11. 운영 환경 설정

마중 운영 서버는 다음 환경변수를 사용한다.

| 환경변수 | 용도 |
| --- | --- |
| `VAPID_PUBLIC_KEY` | 브라우저에 제공할 공개 키 |
| `VAPID_PRIVATE_KEY` | 푸시 인증용 개인 키 |
| `VAPID_SUBJECT` | `mailto:` 또는 `https://` 연락처 |

실제 값은 다음 운영 환경 파일에 설정한다.

```text
/etc/majung/server.env
```

### 활성화 조건

세 환경변수가 모두 올바르게 설정되어 있어야 한다.

일부만 설정했거나 키 형식이 잘못된 경우 서버 기동을 중단한다.

모든 VAPID 설정이 없다면 푸시 기능은 비활성화된 상태로 기존 서비스 기능을 유지한다.

환경 파일을 변경한 뒤에는 해당 설정을 적용하기 위해 서버를 재시작해야 한다.

### VAPID 키 교체

키를 교체하면 이전 공개 키로 만들어진 기존 구독을 새 키로 사용할 수 없다.

따라서 브라우저에서 새로운 공개 키로 다시 구독해야 한다.

운영 키 교체 시에는 기존 구독의 정리와 신규 구독 생성 흐름을 함께 확인한다.

## 12. 데이터베이스 반영

웹 푸시 구독과 발송 기록을 관리하기 위해 `arrival_push` 테이블을 사용한다.

### 신규 데이터베이스

신규 DB의 `initial-schema.sql`에 관련 테이블이 포함되어 있다.

### 기존 데이터베이스

기존 운영 DB에서는 다음 업그레이드 SQL을 적용한다.

```text
db/upgrade-arrival-push.sql
```

### 적용 순서

1. 운영 API 중지
2. PostgreSQL 백업
3. 업그레이드 SQL 검토 및 적용
4. `arrival_push` 테이블 확인
5. 앱 DB 계정 권한 부여
6. 새 서버 JAR 배포
7. 필요 시 VAPID 환경변수 설정
8. 푸시 설정 및 API 확인

### 필요한 DB 권한

- `SELECT`
- `INSERT`
- `UPDATE`
- `DELETE`

VAPID 키를 설정하지 않으면 푸시 구독 테이블을 사용하지 않는다.

다만 배포 프로필은 서버 시작 시 테이블 구조를 검사하므로, 푸시를 비활성화할 예정이어도 새 JAR 배포 전에 스키마를 적용해야 한다.

애플리케이션 배포 과정에서 업그레이드 SQL을 자동으로 실행하지 않는다.

---

## 13. 자동화 테스트

서버 자동화 테스트에서 다음 항목을 확인했다.

### VAPID 및 HTTP 요청

- VAPID 서명 생성
- 공개 키를 이용한 서명 검증
- 인증 헤더 구성
- 빈 푸시 본문
- TTL 처리
- 주소 허용 규칙
- 리다이렉트 차단

### 푸시 서비스 응답

- HTTP 404
- HTTP 410
- HTTP 500
- 리다이렉트 응답

### 발송 조건

- ETA 180초 경계
- 조건 충족 시 한 번 발송
- 동시 갱신 중 중복 발송 방지
- 재구독 이후 중복 발송 방지
- 기능 비활성화 처리

### 구독 생명주기

- 탑승자 연결 종료 시 정리
- 픽업 종료 시 정리
- 명시적 구독 해제
- 마중 요청 기반 계정 구독
- 접근 권한 확인

이 시험은 서버의 발송 로직과 HTTP 처리 정책을 검증한 결과다.

---

## 14. Chrome·FCM 연동 검증

로컬 서버와 헤드리스 Chrome을 이용해 실제 푸시 서비스인 FCM까지 연동을 확인했다.

### 시험 환경

- 로컬 마중 백엔드
- 테스트용 VAPID 키
- 헤드리스 Chrome
- 실제 FCM 푸시 서비스

### 시험 순서

1. 브라우저에서 푸시 구독 생성
2. 서버에 구독 등록
3. 차량 ETA 400초 전송
4. 알림이 발송되지 않는지 확인
5. 차량 ETA 120초 전송
6. 브라우저의 알림 수신 확인

### 결과

| 조건 | 결과 |
| --- | --- |
| 푸시 구독 | 성공 |
| ETA 400초 | 발송 없음 |
| ETA 120초 | 알림 수신 확인 |

테스트용 VAPID 키와 로컬 서버를 사용했지만, 푸시 전달에는 실제 FCM 서비스를 사용했다.

따라서 단순 Mock HTTP 시험과는 구분한다.

다만 실제 사용자의 휴대전화 잠금 화면이나 운영체제 알림 배너가 표시된 결과는 아니다.

---

## 15. 검증하지 않은 범위

현재 기록에는 다음 항목의 검증 결과가 없다.

- 운영 서버 VAPID 키로 실제 알림 수신
- Firefox와 Mozilla Push Service 연동
- Safari와 Apple Push Service 연동
- iPhone 홈 화면 웹앱의 실제 알림 배너
- Android 실기기 백그라운드 알림
- 실제 모바일 네트워크 전환
- 서버·DB 장애 중 알림 전달
- 장기간 사용 후 만료된 구독의 실제 정리 결과

브라우저와 운영체제별 푸시 지원 조건이 다르므로 실제 기기에서는 별도 검증해야 한다.

특히 로컬 Chrome·FCM 시험의 성공을 Safari나 iPhone 알림 수신 성공으로 표현하지 않는다.

## 16. 설계상 제한과 운영 고려사항

### 알림 전달 보장

현재 구현은 중복 발송을 방지하기 위해 `notified_at`을 조건부로 기록한다.

발송 실패 시 자동 재시도하지 않으므로 전달 성공을 보장하는 구조는 아니다.

### 빈 푸시 페이로드

현재는 서비스 워커에 고정된 메시지만 표시한다.

추후 알림에 사용자별 내용을 넣으려면 Web Push 페이로드 암호화와 개인정보 처리 기준을 다시 검토해야 한다.

### 브라우저 의존성

브라우저 알림 권한, 서비스 워커 실행 가능 여부, OS 알림 설정 및 푸시 서비스 상태에 따라 실제 알림 표시가 달라질 수 있다.

### 실시간 위치 공유와의 구분

도착 임박 푸시는 보조 알림이다.

푸시가 실패하거나 도착하지 않더라도 웹의 픽업 상태 조회 및 차량 위치 공유 흐름은 별도로 동작한다.
