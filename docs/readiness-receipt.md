# 준비 상태 전달 확인

탑승자가 누른 준비 상태는 먼저 서버에 저장한다. 차량 앱이 그 상태를 받은 뒤 별도로 수신 확인을 보낸다. 운전자가 읽거나 행동했다는 뜻은 아니다.

## API

`PUT /api/v1/pickups/{id}/readiness-receipt`

차량의 해당 픽업 Bearer 권한이 필요하다. 본문은 `participantId`와 양수 `sequence`다. 응답은 기존 픽업 Snapshot이다. `participant.readinessReceivedSequence`가 추가된다.

- `readinessSequence > readinessReceivedSequence`: 서버 저장 후 차량 수신 대기.
- 두 순번이 같고 양수: 차량 앱 수신 확인.
- 순번 0: 아직 탑승자가 준비 상태를 선택하지 않음.

이전 순번의 확인은 최신 확인을 되돌리지 않는다. 서버에 없는 미래 순번은 409다. 탑승자가 교체되면 수신 순번을 0으로 초기화하며 이전 탑승자 ID의 지연 요청은 409로 거절한다. 탑승자 권한은 403, 종료된 픽업은 410이다. 수신 확인은 차량 위치 정보나 활동 시간을 갱신하지 않는다.

초대 참여와 로그인한 마중 요청은 같은 Pickup 상태를 사용한다. 새 필드를 모르는 기존 클라이언트도 계속 사용할 수 있다. 수신 확인 기능이 없는 이전 APK에서는 대기 상태가 유지된다.

## 배포

DB 백업 후 `src/main/resources/db/add-readiness-receipt.sql`을 먼저 적용한다. 기존 행은 기본값 0이며 수신했다고 추정하지 않는다. 신규 DB 스키마에도 같은 열을 포함한다. 서버 → 웹 → 새 차량 APK 순서로 반영한다.

## 검증

서버 전체 테스트 76건 중 75건 통과, 기존 수동 브라우저 시험 1건 제외. 차량·탑승자 권한 분리, 미래 순번·중복·역순·탑승자 교체·종료, 수신 확인으로 활동 시간이 연장되지 않는 조건을 확인했다. 실제 HTTP 시험과 PostgreSQL 운영 스키마 준비를 구분한다.
