# 만날 장소 변경

탑승자와 운전자는 진행 중인 픽업에 다른 장소를 제안할 수 있다. 제안만으로 현재 장소나 경로를 바꾸지는 않는다.

1. 차량에서 제안 장소를 확인한다.
2. 내비에서 기존 픽업 경유지를 새 장소로 교체한다. 기존 픽업이 최종 목적지였다면 최종 목적지는 두고 새 장소를 첫 경유지로 추가한다.
3. SDK 응답에서 새 장소, 최종 목적지, 다른 경유지의 순서와 예상 시간을 확인한다.
4. 운전자가 차량에서 ‘새 장소 확정’을 누른다.
5. 서버가 장소 버전을 올리고 이전 위치·ETA를 지운다. 차량이 새 장소 기준 정보를 보내면 탑승자에게 표시한다.

## 요청·응답

`PUT /api/v1/pickups/{id}/place-confirmation`은 차량 소유 토큰이 필요하다.

- `proposalId`: 현재 제안의 ID
- `expectedPlaceVersion`: 차량이 확인한 기존 장소 버전
- `place`: SDK에서 확인한 제안 장소의 이름과 좌표
- `durationSeconds`: 새 장소까지 SDK가 응답한 예상 시간
- `sourceTime`: SDK 정보 수신 시각

제안 ID, 기존 버전, 좌표가 일치해야 한다. 경로 정보는 10초 이내여야 한다. 단말과 서버 사이 시계 오차는 미래 5초까지 허용한다. 차량 정보의 유효기간은 서버 수신 시각보다 뒤로 늘어나지 않는다.

같은 제안의 확정을 재전송해도 장소 버전은 한 번만 증가한다. 이미 도착했거나 종료한 픽업에는 새 장소를 확정할 수 없다.

스냅샷과 차량 정보에 `placeVersion`을 반환한다. 장소 변경 후 차량 정보 전송·무효화·도착 요청에도 같은 버전을 보내야 한다. 이전 버전이나 버전 없는 요청은 `PLACE_CHANGED`로 거절한다. 최초 장소인 버전 1에서만 이전 앱 요청을 허용한다.

준비 상태와 차량 수신 확인은 장소 변경과 별개로 유지한다. 도착 알림은 새 장소 기준으로 다시 한 번 신청 상태를 유지하며, 발송 대기 중인 이전 장소 알림은 건너뛴다. 이미 외부 푸시 제공자에게 전달된 알림은 회수할 수 없다.

## 배포 순서

1. DB 백업 후 `add-place-proposal.sql`, `add-place-confirmation.sql`을 순서대로 적용한다.
2. 서버 배포 스크립트의 웹 파일 목록에 `proposal.js`가 포함됐는지 확인한다.
3. 서버 → 웹 순서로 배포하고 새 차량 APK를 설치한다.

이 문서에 적힌 변경은 통합 브랜치 작업이다. 공개 서버 반영과 실제 휴대전화·실차 시험은 별도로 기록한다.

## 변경 도중 앱이 종료된 경우

서버 확정 전에는 이전 장소를 유지한다. 재접속 후 차량에서 제안 장소 확인을 누르면 현재 내비 경로를 다시 읽는다. 제안 ID로 만든 장소 참조와 좌표를 대조하며, 새 장소와 ETA가 확인된 경우에만 확정 버튼을 켠다. 복구 과정에서는 알 수 없는 기존 경로를 임의로 다시 만들지 않는다. 운전자가 현재 경로와 최종 목적지를 확인해야 한다. 좌표·경로 전체를 휴대전화나 차량의 일반 파일에 저장하지 않는다.
