
# 마중 백엔드 Blue-Green 배포

마중 백엔드는 단일 GCP VM에서 두 개의 Spring Boot 서버를 번갈아 실행하는 Blue-Green 배포 방식을 사용한다.

새 버전을 현재 운영 서버와 다른 슬롯에서 실행하고 검증한 뒤, Caddy의 API 연결 대상을 변경한다.

외부 접속 주소는 `https://majung.cloud`로 유지하며 별도의 공개 포트나 VM을 추가하지 않는다.

이 문서는 배포 구조, 운영 전환 절차, 로그인 세션 처리, 최초 설치 및 장애 복구 과정을 정리한 기록이다.

---

## 1. 배포 구조

### 서버 구성

| 구성 요소 | 역할 |
| --- | --- |
| Caddy | HTTPS 요청 수신 및 활성 API 슬롯 연결 |
| Blue | Spring Boot 서버 · 내부 포트 `8081` |
| Green | Spring Boot 서버 · 내부 포트 `8082` |
| PostgreSQL | 서비스 데이터 및 공유 로그인 세션 |
| GitHub Actions | 테스트·빌드·배포 자동화 |
| systemd | 슬롯별 서버 프로세스 관리 |

### 요청 처리 구조

```text
                 사용자 · 차량 앱 · 모바일 웹
                             │
                             ▼
                  https://majung.cloud
                             │
                             ▼
                     Caddy (HTTPS)
                             │
                             ▼
                       /api/ 요청
                             │
                  ┌──────────┴──────────┐
                  │                     │
                  ▼                     ▼
             Blue : 8081          Green : 8082
              활성 슬롯             대기 슬롯
                  │                     │
                  └──────────┬──────────┘
                             │
                             ▼
                        PostgreSQL
                    서비스 데이터 + 세션
```

위 그림은 Blue가 활성 슬롯인 예시다.

Green으로 전환하면 Caddy가 `8082`의 서버로 API 요청을 전달한다.

두 서버는 같은 VM과 데이터베이스를 사용한다.

**이 구조는 애플리케이션 배포 전환을 위한 것으로, VM이나 데이터베이스 장애에 대비한 이중화는 아니다.**

---

## 2. 배포 절차

운영 배포는 GitHub Actions를 통해 진행한다.

### 기본 흐름

1. 현재 요청을 처리하지 않는 슬롯 확인
2. 대기 슬롯에 새 JAR 배포
3. 후보 서버 실행
4. 데이터베이스 연결 및 공유 세션 확인
5. 후보 서버의 커밋 SHA와 슬롯 이름 확인
6. Caddy의 API 연결 대상을 후보 서버로 변경
7. 공개 HTTPS에서 새 버전 및 슬롯 확인
8. 활성 정기 작업 담당 전환
9. 기존 요청 처리를 위해 20초 대기
10. 이전 서버 종료

### 후보 서버 검증

트래픽 전환 전에 다음 항목을 확인한다.

- Spring Boot 서버 기동 여부
- 데이터베이스 연결
- `SPRING_SESSION` 및 `SPRING_SESSION_ATTRIBUTES` 접근
- 배포 대상 커밋 SHA
- 실행 중인 슬롯 이름
- 내부 health 응답

후보 서버가 정상적으로 실행되지 않으면 Caddy 연결 대상을 변경하지 않는다.

### 트래픽 전환

후보 서버의 내부 검증이 끝나면 Caddy의 API 연결을 새 슬롯으로 변경한다.

전환 후 공개 HTTPS에서도 기대한 `revision`과 `slot`이 반환되는지 확인한다.

기존 서버가 정상 응답을 반환했다는 이유만으로 새 버전 배포가 성공했다고 판단하지 않는다.

### 이전 서버 종료

전환이 성공하면 기존 요청 처리를 위해 20초 동안 기다린 뒤 이전 서버를 종료한다.

20초 대기는 전환 시점의 기존 요청을 처리하기 위한 유예 시간이다.

모든 장기 연결이나 요청이 반드시 완료된다는 보장은 아니다.

## 3. 로그인 세션 공유

Blue와 Green은 같은 PostgreSQL 데이터베이스의 Spring Session JDBC 테이블을 사용한다.

### 세션 저장 테이블

```text
SPRING_SESSION
SPRING_SESSION_ATTRIBUTES
```

로그인 세션과 CSRF 정보를 두 서버가 공유할 수 있도록 구성했다.

### 전환 시 동작

- Blue에서 생성한 로그인 세션을 Green에서 확인
- 동일한 CSRF 정보를 이용한 요청 처리
- 한 슬롯에서 로그아웃하면 다른 슬롯에서도 세션 해제
- 서버 전환 후 기존 로그인 상태 유지 지원

세션을 각 서버 메모리에 별도로 저장하지 않으므로 슬롯이 변경되어도 서버마다 로그인 정보가 달라지는 문제를 줄인다.

### 최초 전환 시 주의사항

메모리 기반 세션에서 Spring Session JDBC로 처음 전환할 때는 기존 로그인 사용자가 한 번 다시 로그인해야 할 수 있다.

이후 두 슬롯은 같은 세션 테이블을 사용한다.

차량 접근 권한, 픽업 토큰 및 탑승자 권한은 별도의 데이터베이스 데이터이므로 공유 세션 전환만으로 삭제하지 않는다.

---

## 4. 정기 작업 중복 실행 방지

Blue와 Green이 동시에 실행되는 동안 같은 정기 작업이 중복 수행되지 않도록 관리한다.

### 활성 슬롯 기준

활성 정기 작업 담당은 다음 파일을 기준으로 확인한다.

```text
/etc/majung/active-slot
```

아래 작업은 해당 파일에 지정된 서버에서만 실행한다.

- 픽업 자동 만료
- 종료 데이터 보관 기간 정리
- 차량 연결 코드 정리
- 카카오 연결 해제 재시도

배포 검증 중인 후보 서버는 위 작업을 수행하지 않는다.

### Spring Session 정리

Spring Session 자체의 만료 세션 정리는 두 서버에서 실행할 수 있다.

해당 데이터베이스 삭제 처리는 중복 실행에도 결과가 달라지지 않도록 구성되어 있다.

서비스의 픽업 정기 작업과 Spring Session의 세션 정리는 구분한다.

---

## 5. SSE 연결 처리

마중은 SSE(Server-Sent Events)를 통해 모바일 웹에 상태 변경 신호를 전달한다.

웹은 신호를 받으면 필요한 API를 다시 조회한다.

### 서버 전환 시

Caddy 설정 변경이나 이전 서버 종료 과정에서 기존 SSE 연결이 끊어질 수 있다.

클라이언트는 재연결한 뒤 서버의 현재 상태를 다시 확인해야 한다.

따라서 Blue-Green 배포는 **SSE 연결 자체가 끊기지 않는 것을 보장하지 않는다.**

전환 중 발생한 상태 변경은 재연결 후 서버 재조회로 확인하도록 한다.

## 6. 최초 설치 — 운영자 작업

이 단계는 일반 GitHub Actions 배포에서 자동으로 수행하지 않는다.

운영자가 마중 인스턴스인지 확인하고, 필요한 파일과 권한을 준비한 뒤 최초 전환을 수행한다.

### 6.1 PostgreSQL 백업 및 세션 테이블 준비

운영 데이터베이스를 백업한 뒤 다음 SQL을 적용한다.

```text
src/main/resources/db/upgrade-shared-sessions.sql
```

기존 서비스 테이블은 삭제하지 않는다.

애플리케이션 DB 계정에는 두 세션 테이블에 대한 다음 권한이 필요하다.

- `SELECT`
- `INSERT`
- `UPDATE`
- `DELETE`

### 6.2 공유 세션 적용

기존 `majung.service`에 PostgreSQL 공유 세션을 사용하는 서버 버전을 먼저 배포한다.

세션 저장 방식 변경과 슬롯 전환을 한 번에 처리하지 않고 단계적으로 적용한다.

### 6.3 슬롯 실행 파일 설치

`majung-slot.sh`를 운영자가 검토한 뒤 다음 경로에 설치한다.

```text
/usr/local/libexec/majung-slot
```

설정:

- 소유자: root
- 실행 파일 권한: `755`

systemd 템플릿 파일:

```text
majung@.service.example
```

설치 경로:

```text
/etc/systemd/system/majung@.service
```

설치 후 systemd 설정을 다시 읽는다.

```sh
sudo systemctl daemon-reload
```

### 6.4 슬롯 디렉터리 준비

다음 디렉터리를 생성한다.

```text
/opt/majung/slots/blue
/opt/majung/slots/green
```

파일 및 디렉터리 권한:

| 대상 | 소유자 | 권한 |
| --- | --- | --- |
| 슬롯 디렉터리 | root | `755` |
| `server.jar` | root | `644` |

현재 검증된 JAR를 다음 경로에 배치한다.

```text
/opt/majung/slots/blue/server.jar
```

환경변수는 기존 root 전용 `server.env`를 사용한다.

운영 비밀 정보를 슬롯별 JAR나 GitHub Actions 아티팩트에 포함하지 않는다.

### 6.5 Blue 서버 실행

정기 작업 담당을 우선 `standalone`으로 유지한 상태에서 Blue 서버를 시작한다.

내부 health에서 다음 항목을 확인한다.

- 서버 상태
- 커밋 SHA
- 실행 슬롯
- 데이터베이스 연결
- 공유 세션 테이블

### 6.6 Caddy 연결 변경

기존 Caddy의 API `reverse_proxy` 블록을 다음 import 방식으로 변경한다.

```caddy
import /etc/caddy/majung-upstream.caddy
```

`/etc/caddy/majung-upstream.caddy`는 최초 설치 시 Blue의 `8081` 포트를 대상으로 하는 `reverse_proxy` 블록이다.

기존 연결 및 응답 시간 제한은 유지한다.

Caddy 설정을 검증한 뒤 reload하고 공개 health 응답을 확인한다.

### 6.7 활성 슬롯 전환

공개 서버에서 Blue의 버전과 슬롯이 확인되면 다음 상태를 갱신한다.

- `/etc/majung/active-slot` → `blue`
- `active-backend.json` → 활성 슬롯 및 커밋 SHA

이후 기존 `majung.service`를 종료하고 비활성화한다.

Blue 서비스는 재부팅 시 시작하도록 활성화한다.

### 6.8 배포 프로그램 교체

root 소유의 배포 프로그램을 현재 `deploy/release.py` 버전으로 교체한다.

기존 배포 정책의 다른 설정은 유지하고 다음 항목만 변경한다.

```json
{
  "backend_mode": "blue-green"
}
```

위 JSON은 변경할 항목을 보여주는 예시다.

기존 `deploy-policy.json` 파일 전체를 이 내용으로 덮어쓰지 않는다.

## 7. systemd 서비스 관리

슬롯 전환 시 새 활성 서비스와 이전 서비스를 구분한다.

새로운 활성 슬롯은 재부팅 시 시작하도록 enable하고 이전 슬롯은 disable한다.

### 서비스 상태 확인

```sh
systemctl status majung@blue majung@green
```

### 종료 코드 처리

이전 JVM이 종료 신호를 받은 후 종료 코드 `143`으로 끝나는 경우가 있다.

정상적인 배포 종료를 실패 상태로 기록하지 않도록 systemd 서비스 예시에 다음 설정을 사용한다.

```ini
SuccessExitStatus=143
```

이 설정은 정상 종료로 허용할 종료 코드를 지정하는 것이며, 모든 비정상 종료를 성공으로 간주하는 설정은 아니다.

## 8. 배포 실패와 복구

### 후보 서버 기동 실패

후보 서버가 정상적으로 시작하지 못하면 Caddy 연결 대상을 바꾸지 않는다.

기존 활성 슬롯에서 요청 처리를 계속한다.

### 공개 health 확인 실패

Caddy를 새 슬롯으로 전환한 뒤 공개 health에서 예상 커밋이나 슬롯을 확인하지 못하면 기존 연결 대상으로 복구한다.

활성 정기 작업 담당도 기존 슬롯으로 되돌린다.

### Caddy 설정 변경 실패

설정 검증 또는 reload에 실패하면 기존 Caddy 설정을 복구한다.

공개 health에서 기존 서버가 정상적으로 응답하는지 확인한다.

### 최초 설치 실패

최초 `standalone → blue` 전환에 실패하면 다음 상태를 복구한다.

1. 백업한 Caddy 설정 복원
2. 이전 배포 정책 복원
3. 기존 `majung.service` 재시작
4. 공개 health 확인

기존 데이터베이스 세션 테이블은 삭제하지 않는다.

### 복구 범위

Blue-Green 복구는 애플리케이션 실행 대상과 프록시 설정을 되돌리는 절차다.

데이터베이스 스키마나 데이터 변경까지 자동으로 되돌리지는 않는다.

## 9. 운영 상태 확인

### 공개 health

```sh
curl -fsS https://majung.cloud/api/v1/health
```

확인 항목:

- `status`
- `revision`
- `slot`

새 배포가 성공했는지 판단할 때는 예상 커밋 SHA와 실제 슬롯이 모두 일치해야 한다.

### 운영 상태 파일

| 파일 | 용도 |
| --- | --- |
| `/etc/majung/active-slot` | 정기 작업 담당 슬롯 |
| `/var/lib/majung-deploy/active-backend.json` | 활성 슬롯 및 배포 커밋 |
| `/etc/caddy/majung-upstream.caddy` | 실제 API 연결 대상 |

파일의 내용이 서로 일치하지 않으면 배포를 진행하지 않는다.

설정·상태 파일은 root만 변경할 수 있도록 관리한다.

운영 환경변수, 로그인 쿠키 및 DB 세션 내용은 로그나 GitHub에 공개하지 않는다.

---

## 10. 데이터베이스 변경 시 주의사항

Blue-Green 배포 중에는 신규 코드와 기존 코드가 일정 시간 같은 데이터베이스에 접근할 수 있다.

따라서 스키마를 변경할 때 두 버전의 호환성을 고려해야 한다.

### 권장 적용 순서

1. 운영 데이터베이스 백업
2. 기존 코드와 호환되는 컬럼 및 테이블 추가
3. 신규 코드 배포
4. 필요한 데이터 이관
5. 기존 코드 의존성 제거 확인
6. 호환되지 않는 스키마 변경 별도 진행

이전 서버가 사용하는 컬럼을 바로 삭제하거나 이름을 변경하면 배포 복구 시 이전 코드가 정상적으로 동작하지 않을 수 있다.

코드 롤백과 DB 마이그레이션 롤백은 구분한다.

---

## 11. 자동화 테스트

배포 로직에 대해 다음 상황을 자동화 테스트로 확인했다.

- 후보 서버 기동 실패
- 공개 health 검증 실패
- Caddy reload 실패
- 실패 시 기존 슬롯 복구
- 같은 커밋 SHA 재배포
- 예상 슬롯 검증
- 동일 DB를 사용하는 두 HTTP 서버
- 공유 로그인 세션
- CSRF 정보 공유
- 로그아웃 동기화

복구 관련 테스트는 실제 운영 장애를 발생시키지 않고 시험 환경에서 진행했다.

자동화 테스트 통과가 운영 환경의 모든 장애 복구 성공을 보장하는 것은 아니다.

---

## 12. 최초 운영 전환 결과

**검증일: 2026년 10월 29일**

마중 운영 서버에서 기존 단일 서버 실행 방식에서 Blue 슬롯으로 처음 전환했다.

### 적용 과정

1. 운영 PostgreSQL 백업
2. Spring Session JDBC 테이블 준비
3. 필요한 DB 권한 추가
4. 기존 서비스의 공유 세션 사용 확인
5. Blue 서버 실행 및 검증
6. Caddy API 연결 대상 변경
7. 활성 슬롯 상태 기록
8. 기존 standalone 서비스 종료

### 검증 결과

| 항목 | 결과 |
| --- | --- |
| 운영 전환 | `standalone → blue` 성공 |
| 공개 health 조회 | 70회 모두 HTTP 200 |
| 배포 커밋 확인 | 일치 |
| 활성 슬롯 확인 | 일치 |
| 기존 익명 세션·CSRF 처리 | 전환 후 로그아웃 성공 |
| DB 공유 세션 | 확인 |

전환 중 공개 health 70회 모두 HTTP 200을 반환했다.

또한 전환 전에 발급한 익명 세션과 CSRF 정보로 전환 후 로그아웃 요청이 처리되는 것을 확인했다.

**이 결과는 해당 전환 시험 구간에서 관찰한 값이다. 모든 사용자 요청이 모든 장애 상황에서 무중단으로 처리된다는 뜻은 아니다.**

### 장애 복구 검증 범위

후보 서버 기동 실패, 공개 health 확인 실패, Caddy reload 실패에 대한 복구는 자동화 테스트로 확인했다.

운영 서버에서 해당 장애를 인위적으로 발생시키지는 않았다.

## 13. 현재 구조의 한계

마중의 Blue-Green 배포는 운영 코드 전환과 배포 실패 복구를 위한 구조다.

다음 항목은 별도로 해결해야 한다.

- GCP VM 자체의 장애
- PostgreSQL 장애
- 장기 실행 요청의 완전한 무중단 보장
- SSE 연결의 지속 유지
- 데이터베이스 스키마 자동 롤백
- 실제 장애 상황에서의 전체 복구 시간 측정

현재 구성은 **단일 VM·단일 데이터베이스의 Blue-Green 배포**로 설명하는 것이 정확하다.
